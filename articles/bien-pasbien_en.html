❌ Not Good

Naming variables in abbreviated form or with no concrete meaning

❌ Magic Number {% include "bien-pasbien-magic-number.html" %}

❌ Not Good

Not allowing a rollback in case of a crash before the commit in the database

✅ ACID: Atomicity

If the first query succeeds and the server crashes before the second one:

  • Account [id = 1] is debited
  • Account [id = 2] is not credited

➡️ Money lost

SQL UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- Server outage here, or app crash UPDATE accounts SET balance = balance + 100 WHERE id = 2;

❌ Not Good

Duplicating code instead of factoring it out

✅ Good

Documenting your code and keeping it intuitive

✅ KISS: Keep It Simple Stupid
JavaScript function calculateVAT(preTaxPrice) { // Calculates VAT for a pre-tax price return preTaxPrice * 0.2; }
Python def calculate_vat(pre_tax_price): """Calculates VAT for a pre-tax price""" return pre_tax_price * 0.2
C# public double CalculateVAT(double preTaxPrice) { // Calculates VAT for a pre-tax price return preTaxPrice * 0.2; }

❌ Not Good

Too much logic in a single function/class

✅ SRP: Single Responsibility Principle (SOLID)
JavaScript function processUserData() { // Read the data // Validate the data // Compute stuff // Generate a report // Send an email ... }
Python def process_user_data(): # Read the data # Validate the data # Compute stuff # Generate a report # Send an email ...
C# public void ProcessUserData() { // Read the data // Validate the data // Compute stuff // Generate a report // Send an email ... }

✅ Good

Applying clean code principles

✅ GRASP: General Responsibility Assignment Software Patterns
  1. Information Expert — assign responsibility to the class that has the necessary information
  2. Creator — the class that creates an object
  3. Controller — handle the system's events
  4. Low Coupling — minimize dependencies between classes (encapsulation)
  5. High Cohesion — a class should have a well-focused responsibility
  6. Polymorphism — use polymorphism to handle variations
  7. Pure Fabrication — create artificial classes to avoid strong coupling or responsibilities that don't belong to domain classes
  8. Indirection — use an intermediate class to reduce dependencies
  9. Protected Variations — protect unstable elements behind interfaces or abstractions

❌ Not Good

Not respecting database constraints before and after a transaction

✅ ACID: Consistency
SQL CREATE TABLE accounts ( id INTEGER PRIMARY KEY, balance INTEGER ); -- A negative balance should not be allowed in a banking context BEGIN; UPDATE accounts SET balance = balance - 200 WHERE id = 1; COMMIT;

✅ Good

Catching errors

✅ Fail Fast {% include "bien-pasbien-fail-fast.html" %}

❌ Not Good

Modifying existing code instead of extending it

✅ OCP: Open/Closed Principle (SOLID)
JavaScript function calculatePrice(cart, customerType) { if (customerType === "pro") { return cart * 0.9; } else if (customerType === "vip") { return cart * 0.8; } else { return cart; } }
Python def calculate_price(cart, customer_type): if customer_type == "pro": return cart * 0.9 elif customer_type == "vip": return cart * 0.8
C# public static double CalculatePrice(double cart, string customerType) { if (customerType == "pro") { return cart * 0.9; } else if (customerType == "vip") { return cart * 0.8; } else { return cart; } }

✅ Good

Not inheriting from a class that doesn't respect the contract or expected behavior of the parent class

✅ LSP: Liskov Substitution Principle (SOLID)
JavaScript class Customer { calculatePrice(cart) { return cart; } } class ProCustomer extends Customer { calculatePrice(cart) { return cart * 0.9; } } class VipCustomer extends Customer { calculatePrice(cart) { return cart * 0.8; } } [ new Customer(), new ProCustomer(), new VipCustomer() ] .forEach(c => console.log(c.calculatePrice(100)));
Python class Customer: def calculate_price(self, cart): return cart class ProCustomer(Customer): def calculate_price(self, cart): return cart * 0.9 class VipCustomer(Customer): def calculate_price(self, cart): return cart * 0.8 for customer in [Customer(), ProCustomer(), VipCustomer()]: print(customer.calculate_price(100))
C# using System; class Customer { public virtual double CalculatePrice(double cart) => cart; } class ProCustomer : Customer { public override double CalculatePrice(double cart) => cart * 0.9; } class VipCustomer : Customer { public override double CalculatePrice(double cart) => cart * 0.8; } class Program { static void Main() { Customer[] customers = { new Customer(), new ProCustomer(), new VipCustomer() }; foreach (var c in customers) Console.WriteLine(c.CalculatePrice(100)); } }

❌ Not Good

An interface/class too large, imposed on everyone

✅ ISP: Interface Segregation Principle (SOLID)
JavaScript class Animal { eat() { } fly() { } } class Cat extends Animal { fly() { // Useless for a cat } }
Python class Animal: def eat(self): pass def fly(self): pass class Cat(Animal): def fly(self): # Useless for a cat pass
C# public abstract class Animal { public abstract void Eat(); public abstract void Fly(); } /* public interface IAnimal { void Eat(); void Fly(); } */ public class Cat : Animal { public override void Eat() { // Eats normally Console.WriteLine("Cat is eating"); } public void Fly() { // Useless for a cat but must be implemented } }

✅ Good

The model stores the data, the view displays it, and the controller creates it

✅ MVC: Model View Controller {% include "bien-pasbien-mvc.html" %}

❌ Not Good

Allowing "dirty reads" (reading uncommitted data), "non-repeatable reads" (re-reading data modified by another transaction), "phantom reads" (new rows appearing in a repeated query)

✅ ACID: Isolation
SQL -- Transaction 1 BEGIN; SELECT balance FROM accounts WHERE id=1; -- reads 100 UPDATE accounts SET balance = balance - 80 WHERE id=1; -- Not committed yet -- Transaction 2 (concurrent) BEGIN; SELECT balance FROM accounts WHERE id=1; -- also reads 100 UPDATE accounts SET balance = balance - 80 WHERE id=1; COMMIT; -- Transaction 1 commits after, overwrites T2's change COMMIT;

❌ Not Good

...not to friends of friends (too many calls)

✅ LoD: Law of Demeter {% include "bien-pasbien-lod-friends.html" %}

❌ Not Good

✅ ACID: Durability
SQL BEGIN TRANSACTION UPDATE accounts SET balance = balance - 100 WHERE id = 1 UPDATE accounts SET balance = balance + 100 WHERE id = 2 COMMIT -- Data committed but server crash before disk write -- A mechanism like the Write-Ahead Log (WAL) is needed -- Even if the machine crashes right after, the changes can be recovered on restart by replaying this log

✅ Good

Classes should not depend on other classes but on interfaces or abstract classes

✅ DIP: Dependency Inversion Principle (SOLID) {% include "bien-pasbien-dip-js.html" -%}
Python class MessageService: def send(self, message): pass class EmailService(MessageService): def send(self, message): print(f"Email sent: {message}") class OrderManager: def __init__(self, service): self.service = service def notify(self): self.service.send("Order confirmed")
C# public interface IMessageService { void Send(string message); } public class EmailService : IMessageService { public void Send(string message) { Console.WriteLine($"Email sent: {message}"); } } public class OrderManager { private readonly IMessageService _service; public OrderManager(IMessageService service) { _service = service; } public void Notify() { _service.Send("Order confirmed"); } }

❌ Not Good

Coding a feature now because you think it will be useful later

YAGNI: You Aren't Gonna Need It
JavaScript function calculateTotal(price, tax, discount = 0, birthdayBonus = 0) { const total = price + (price * tax); // The other parameters serve no purpose for now return total; }
Python def calculate_total(price, tax, discount=0, birthday_bonus=0): total = price + (price * tax) # The other parameters aren't used yet return total
C# public decimal CalculateTotal(decimal price, decimal tax, decimal discount = 0, decimal birthdayBonus = 0) { decimal total = price + (price * tax); // The other parameters are unused for now return total; }

What is a MSC application ?
With the ubiquity of digital technology in our lives, protecting computer systems has become a necessity. But ensuring their safety is not just about putting protections in place initially : they need to be monitored and updated regularly to avoid incidents. That’s where Maintenance in Security Condition (MSC, originally MCS in French) comes in, a process of reducing flaws that can be exploited by cyber attacks, commonly known as vulnerabilities. Meanwhile, Maintenance in Operational Condition (MOC, originally MCO in French) aims to ensure that computer equipments such as servers or networks run properly and sustainably. In summary, MOC focuses on good technical running while MSC focuses on protection against external threats. Both are essential : an unresolved failure can leave a door open to attack and an unpatched vulnerability can take an entire system out of service. In this article, we’ll explore what a MSC application is, why it’s essential for any organization and how it can help make digital infrastructures more secure in the long run.

The rise of cyber threats becoming more and more acute today, using tools so as to alert businesses and institutions has become a must. Indeed, according to an article from « Le Monde » dated May 27th 2020, mail and SMS scams during confinement almost increased 5-fold ! MSC applications come into action to ensure safety, quality and scalability but what is it exactly ? A MSC app aims to alert an organization when a risk appears on a environment defined by one of its employees so as to automate and facilitate decision support mechanisms. It is generally articulated in 4 parts :

  • the « Feed » part, responsible for vulnerability monitoring (scripting)
  • the « UI » part, equivalent to the user interface (front-end)
  • the « API » part, dedicated to managing user requests and including notably the risk calculation or CVSS module (back-end)
  • the « DB » part, storing API data (database)

It uses a REST API that sends responses in JSON and uses a secure protocol to authenticate users (for instance, OAuth2 with Python) and the HTTP (HyperText Transfer Protocol) to communicate. The application is based on a client-server architecture and linking to at least one database (for example, PostgreSQL or Elasticsearch). The server designates the entire API while the client represents the software that sends requests to the API. Primary objectives are confidentiality, maintainability but also a fine-grained management of the actions that users are entitled to perform (CRUD - creation, reading, update or removal of resources) and a setting up of the app from the database.

As a reminder, there are six architectural constraints which define a REST system :

  1. Separated responsibilities between client and server

    That constraint supports the multiplicity of organizational domains required across the Internet and improves user interface portability across multiple platforms.

  2. No session state retention

    Each request therefore contains all the information necessary for the server to respond to it and there is no need to maintain a permanent connection between the client and the server. However, authentication is more complex to manage, requiring tokens to be passed on each time a request is made. The operation of the latter will be described later.

  3. Cacheability

    Performance and scalability are greatly improved because caching often avoids redundant queries, server overhead and bandwidth waste.

  4. Division into layers

    The client must be unaware of the nature of the server to which it is connected (staging or final). A staging server can improve system scalability by implementing load balancing and a shared cache or also step security policies up.

  5. Uniform interface

    As a fundamental constraint, it uncouples the architecture, allowing components to scale independently. It is divided into four parts :

    • Identification of the resources in queries through an URI

      The resources themselves are conceptually distinct from the representations that are returned to the client. Remember that a URI (Uniform Resource Identifier) is a short identifier of a resource on a physical or abstract network and whose syntax complies with the Internet standards established by the WWW (World Wide Web). An URI can be either a « locator » (URL) or a « name » (URN) or both. Here, the URI is nothing more than the address where the database with which the API will interact is located.

    • Manipulation of the resources by representations

      Each representation of a resource provides sufficient information to the client so as to modify or delete the resource.

    • Self-descriptive messages

      Each message contains enough information to know how to interpret it.

    • Hypermedia as application status engine (HATEOAS)

      After accessing an initial URI of the application, similar to humans accessing the home page of a website, the client must be able to dynamically use the hyperlinks provided by the server to discover all possible actions and resources it needs to continue browsing.

  6. With upon request code (optional constraint)

    The server can transfer executable code to the client. This improves system scalability but reduces the visibility of the resource organization and is therefore optional.

We’ll now go into the details of how the OAuth2 protocol, commonly used to authenticate API users, works. This free protocol allows the client to use the API and works with tokens. A token is a long, encrypted string of characters that allows the stateless constraint to be implemented by being passed in each request from the client to the server. First, it is important to distinguish between authentication and identification. The first allows the system to validate the legitimacy of access to the entity while the second gives rise to the recognition of the entity whose identity has been defined previously.

  • Authentication stage

    First, the mechanism uses the authentication information : email and password. After these checks, it creates a token with base defaults that will be dependent on the authentication context (which user is logged in ?). A token is returned and serves as the user identification for each request to the API server.

  • Identification stage

    This is a fine-grained user rights management. When a request is sent to the API server, several checks will be performed :

    • First of all, we check :
      • user identity
      • that the supplied token is correct
      • resource existence
      • if the desired action is an action implemented within the API
    • Authorization is then checked in order of priority :
      • of the user to log in through the application
      • of the application to perform the resource action
      • of the user to perform the resource action in relation to the contract and application
      • of the user to perform the resource action in relation to the contract and application, according to a role

    So some credentials or authorization checks are performed multiple times. This is necessary, although maintenance is added. It is essential for a company or an institution to add security measures to the API operation. It is often important to increase security and performance, even at the expense of maintenance if necessary.

Finally, we will define the variables that are typically used in a MSC application. On the one hand, environments and contexts are directly defined by the user and are therefore abstract variables. On the other hand, CPE, CVE and CVSS appear in NVD (National Vulnerability Database) and will be recovered via scripts executed regularly (preferably daily). Like JVNDB (Japanese Vulnerability National Database), it aims to catalog, maintain and distribute information about discovered vulnerabilities which target real computer systems.

  • Environment (ENV)

    An environment is defined as the client perimeter, namely the « zone » which contains the set of hardwares and system softwares of a company. It has one or more contexts. For example, a DMZ (Demilitarized Zone) is a subnet separated from the local area network and isolated from the local area network (LAN) and the Internet (or another network) by a firewall. This filtered subnet includes machines that can be accessed from the Internet without the need for LAN access.

  • Context (CONT)

    A context can be a business application or BO (Business Object), a framework, a library.... It contains one or more softwares or CPE. After defining an environment and a context, the user associates the CPE with the context and all the characteristics derived from it. Collecting this data allows you to have information about existing vulnerabilities on a product that a customer (or a user) places in a given environment and context. This is equivalent to assessing the potential danger created by the vulnerability under investigation and providing a necessary workaround (for example, downloading patches).

  • CPE

    The CPE (Common Platform Enumeration) can be chosen :

    • an application (« part » : « a »)
    • a hardware platform (« part » : « h »)
    • an operating system (« part » : « o »)

    It must be as close as possible to the version actually installed. Each CPE has one or more CVEs. It is made unique by an URI that can be of 2 versions (V2 or V3) and according to the standards described by the NIST CPE database.

  • CVE

    The CVE (Common Vulnerabilities and Exposure) defines the vulnerability of at least one CPE. This information includes creation date, release date, update date, description, part numbers, affected products and CVSS metrics.

  • CVSS

    The CVSS (Common Vulnerability Scoring System) can be used to assess the criticality of vulnerabilities based on objective, measurable criteria such as access complexity or presence or absence of privileges. It establishes three scores per version (V2 and V3) : the impact score, the exploitability score and the base score that results from the other two. The above-mentioned scores are calculated from ratios defined for particular parameters such as access complexity and authentication. For more information, click on NVD vulnerability metrics.

To conclude, a MSC application embodies a structured and proactive approach so as to anticipate and mitigate IT vulnerabilities. By combining continuous monitoring, decision automation and fine-grained rights management, it enables organizations to better control their digital environments.
